有段时间我很热衷于技术选型。看到一个新框架就想在下一个项目里用上，理由通常是"它更快"或者"它更现代"。

后来踩了几次坑，慢慢想明白一些事。

## 「更好」是个伪命题

"React 和 Vue 哪个更好"、"PostgreSQL 和 MySQL 怎么选" —— 这类问题之所以没有答案，是因为**缺少约束条件时，比较没有意义**。

真正有价值的问法是：

```text
我们有 3 个前端，其中 2 个熟 Vue
项目要维护 3 年以上
需要 SSR
团队没有专职运维
—— 在这个条件下选什么？
```

约束列出来，答案往往自己就出来了。

## 我实际会看的几个因素

按重要性排序：

### 1. 团队熟悉度

这一条的权重远超大多数人的估计。一个团队熟到能写出高质量代码的技术，和一个只是"听说过"的技术，产出差距是数量级的。

我见过为了用某个新框架，整个团队花了两个月熟悉生态，期间产出的代码质量明显下降，最后写出来的东西跟用老技术没什么区别。

> 技术的价值在于解决问题，不在于它本身。团队不熟的技术，解决问题的效率一定更低。

### 2. 出问题时的可控性

这是我后来加的一条，也是权重上升最快的一条。

选一个技术之前，我会问：**它出问题时，我能不能自己修？**

```text
依赖一个 npm 包      → 可以看源码，可以 fork，可控性高
依赖一个 SaaS 服务   → 只能提工单等，可控性低
依赖一个闭源 SDK     → 完全不可控
```

不是说不能用 SaaS，而是要清楚代价。选之前先想清楚：如果它挂了，我的业务会停多久？

### 3. 生态的健康度

看几个具体指标：

```bash title="判断包是否还在维护"
npm view <package> time.modified   # 最近发布时间
npm view <package> maintainers    # 维护者数量
npm view <package> dependencies   # 依赖了多少东西
```

一个健康的项目通常：最近 6 个月有发布、维护者 ≥ 3、依赖数量适中。

依赖数量这条容易被忽略。一个装进来会带上 80 个传递依赖的库，意味着你的 `node_modules` 里多了 80 个可能出问题的地方。

### 4. 迁移成本

这个最容易被低估，因为它是**未来才付出的成本**，而选型时人天然会低估未来。

我的评估方式是问一个问题：**如果这个技术两年后不维护了，我要花多久迁走？**

- 如果只是个格式化日期的库 → 一天，无所谓
- 如果是整个数据层 → 半年，要慎重
- 如果是框架本身 → 重写，基本不考虑

**越靠近核心，越要选保守的技术。**

## 关于「新技术红利」

有个说法是"用新技术能获得先发优势"。我的观察是，这个红利存在，但**只对特定类型的项目有效**。

```text title="新技术红利的适用范围"
适合尝新的项目：
  - 内部工具，挂了不影响业务
  - 短期项目，生命周期 < 1 年
  - 有明确痛点的场景，新技术正好解决

不适合尝新的项目：
  - 核心业务系统
  - 要长期维护的项目
  - 团队规模大、流动率高的项目
```

一个判断标准：**这个项目的失败成本有多高？** 失败成本低，随便试；失败成本高，选成熟的。

## 一个反直觉的经验

我逐渐形成的一个习惯是：**基础设施选无聊的技术，产品特性选激进的技术。**

```text title="分层的技术策略"
基础设施层
  数据库、消息队列、部署方式
  → 选用了十年以上、有大量生产验证的
  → PostgreSQL / Redis / Docker

产品特性层
  前端框架、交互方案、可视化
  → 可以激进，因为改起来成本低
  → 试错代价可控，收益直接可见
```

理由是：**越底层的东西越难换**。数据库选错了，三年后发现要迁移，那是个大工程。前端框架选错了，最多是重写几个页面。

## 怎么避免过度设计

选型时最容易犯的错，是为**想象中的未来需求**买单。

```text title="过度设计的典型思路"
「我们以后可能会有千万用户，所以现在就要上微服务 + 分库分表 + 消息队列」

实际情况：
  - 两年后日活 3000
  - 多花的时间：6 个月
  - 多增加的运维复杂度：永久性
```

我的做法是：**为当前规模的 10 倍设计，不为 1000 倍设计。**

10 倍是可以通过加机器、加索引、优化查询解决的。1000 倍才需要架构重构。而从 10 倍到 1000 倍，你大概率会有足够的时间和资源来改。

## 最后

技术选型这件事，我现在的原则很简单：

> **选团队能驾驭的、出了问题能自己修的、迁移成本可接受的。**

不追求最优解，只追求在当前约束下足够好且能改的解。

因为大部分时候，**能不能把东西做出来并稳定运行，比用了什么技术重要得多**。
